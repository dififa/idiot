MODUL: AUTHENTICATION & LOGIN (CORE MODULE)
================================================================================

[GOAL]
Menyediakan gerbang autentikasi yang aman, fleksibel, dan persisten via 
kredensial lokal (email/password) maupun Google OAuth; terlindung dari serangan 
brute force; mendukung pemulihan akun via OTP WhatsApp; menjaga kenyamanan sesi 
pengguna melalui Remember Me dan navigasi presisi Intended URL; serta membatasi 
akses modul berproteksi di seluruh framework.

--------------------------------------------------------------------------------
[ACTION]

1. Routing & Antarmuka:
   - Endpoint login/logout: GET /login, POST /login, GET|POST /logout.
   - Endpoint Google OAuth: GET /auth/google, GET /auth/google/callback.
   - Endpoint WhatsApp OTP: GET|POST /forgot-password, GET|POST /reset-password.
   - Form Login UI: Input kredensial, proteksi CSRF token, checkbox "Remember Me", 
     tombol "Masuk dengan Google", tautan "Lupa Password?", serta tautan dinamis 
     ke /signup (hanya muncul jika config('allow_registration') bernilai true).

2. Intended URL Handling:
   - Middleware/Auth Guard menyimpan URI tujuan saat user belum login mencoba 
     mengakses route berproteksi: $_SESSION['intended_url'] = $_SERVER['REQUEST_URI'].
   - Redirect pasca-login: jika $_SESSION['intended_url'] tersedia, arahkan ke URL 
     tersebut dan hapus dari sesi; jika tidak ada, lempar ke /dashboard.

3. Remember Me (Persistent Login):
   - Buat tabel 'user_tokens' (id, user_id, selector, hashed_validator, expires_at).
   - Saat dicentang: generate token selector & validator acak, simpan hash validator 
     ke database, lalu pasang cookie 30 hari di browser.
   - Autologin check pada core bootstrap: verifikasi cookie token saat session user 
     kosong, lalu inisialisasi session jika token valid.

4. Rate Limiting & Account Status Guard:
   - Catat kegagalan login berdasarkan kombinasi IP Address dan Email.
   - Blokir request POST /login selama 15 menit jika terjadi 5 kali kegagalan beruntun.
   - Cek status akun di database: tolak login dengan pesan khusus jika user berstatus 
     'banned' atau 'inactive'.
   - Gunakan pesan error generik ("Email atau password salah") jika kredensial tidak cocok.

5. Google OAuth 2.0:
   - Generate URL otorisasi dengan state token di sesi untuk mencegah serangan CSRF.
   - Di route callback: tukar authorization code menjadi access_token, ambil profil user.
   - Account linking: jika email cocok dengan user lama, update 'google_id'. Jika belum 
     ada, daftarkan otomatis (auto-provisioning) dengan role 'member' dan password NULL.

6. Reset Password via WhatsApp OTP:
   - Validasi ketersediaan kolom nomor WhatsApp di tabel 'users'.
   - Buat tabel 'password_resets' (phone, token, expires_at).
   - Kirim OTP 6-digit via WhatsApp Gateway API dengan masa berlaku 10 menit.
   - Terapkan cooldown pengiriman ulang minimal 60 detik per nomor telepon.

7. Session Security & Audit Trail:
   - Pasang parameter cookie session: httponly=true, samesite=Lax, secure=HTTPS.
   - Eksekusi session_regenerate_id(true) segera setelah login berhasil.
   - Catat last_login_at dan last_login_ip di tabel 'users'.
   - Saat logout: session_destroy(), hapus token Remember Me dari database dan cookie.

--------------------------------------------------------------------------------
[TARGET / DEFINITION OF DONE]

[ ] User berhasil login dengan kombinasi email & password yang valid.
[ ] User berhasil login satu klik via Google OAuth tanpa duplikasi akun email.
[ ] User yang belum login dan mengakses halaman internal diarahkan ke /login, lalu 
    otomatis dikembalikan ke halaman semula setelah login sukses (Intended URL).
[ ] User yang mencentang "Remember Me" tetap login meski browser ditutup/reboot.
[ ] Form login terkunci otomatis selama 15 menit jika salah input 5 kali beruntun.
[ ] Akun dengan status 'banned' atau 'inactive' diblokir dari proses login.
[ ] User bisa mereset password menggunakan kode OTP yang diterima via pesan WhatsApp.
[ ] Token reset WhatsApp hangus setelah 10 menit atau setelah berhasil dipakai 1 kali.
[ ] Tombol/link SignUp otomatis tersembunyi jika registrasi ditutup di Global Config.
[ ] Logout membersihkan seluruh session, cookie browser, dan record token persistensi.

================================================================================
MODUL: SIGNUP / REGISTRATION (CORE MODULE)
================================================================================

[GOAL]
Menyediakan alur pendaftaran mandiri bagi pengunjung publik dengan validasi data 
yang ketat (termasuk verifikasi format nomor WhatsApp); terlindung dari serangan 
bot/spam; memberikan role awal dengan hak akses terendah; serta tunduk penuh pada 
kontrol toggle registrasi di Global Config.

--------------------------------------------------------------------------------
[ACTION]

1. Routing & Antarmuka:
   - Endpoint pendaftaran: GET /signup dan POST /signup.
   - Form UI: Input Nama Lengkap, Email, Nomor WhatsApp, Password, dan Konfirmasi 
     Password. Sertakan CSRF token dan tautan navigasi balik ke /login ("Sudah punya 
     akun? Masuk di sini").

2. Global Config Gatekeeper:
   - Pasang filter di controller/middleware sebelum halaman dirender:
     Jika config('allow_registration') bernilai false, cegah proses pendaftaran, 
     tampilkan halaman informasi "Registrasi sedang ditutup", atau redirect ke /login 
     disertai flash message.

3. Validasi & Sanitasi Input:
   - Email: Wajib format email valid dan belum terdaftar di tabel 'users'.
   - Nomor WhatsApp: Validasi format nomor (format internasional/lokal, misal 08xx/628xx), 
     wajib unik agar fitur OTP reset password tidak salah sasaran.
   - Password: Wajib minimal 8 karakter dan bernilai identik dengan konfirmasi password.
   - Sanitasi input nama untuk mencegah injeksi XSS.

4. Pertahanan Anti-Bot & Rate Limiting:
   - Honeypot Trap: Pasang satu input tersembunyi via CSS (misal name="website_url"). 
     Jika field ini terisi saat form di-submit, sistem langsung menggagalkan proses 
     tanpa memproses database (indikasi spam-bot).
   - Registration Rate Limit: Batasi pengiriman form signup maksimal 3-5 kali per 
     jam dari IP Address yang sama untuk mencegah pembajakan database lewat script.

5. Penyimpanan Data & Proteksi Hak Akses (Least Privilege):
   - Enkripsi password menggunakan password_hash($password, PASSWORD_BCRYPT/ARGON2ID).
   - Kunci penetapan role secara mutlak di backend ke level terendah: 'member'. 
     Abaikan parameter role apa pun yang dikirim lewat form request.
   - Set status akun default ke 'active' (atau 'pending' jika butuh verifikasi admin).

6. Alur Pasca-Daftar (Post-Registration Flow):
   - Auto-Login UX: Begitu data tersimpan, regenerasi sesi dan langsung inisialisasi 
     session user (otomatis login) lalu lempar ke /dashboard; ATAU
   - Redirect Login: Lempar user ke halaman /login dengan notifikasi sukses "Akun 
     berhasil dibuat, silakan masuk".

--------------------------------------------------------------------------------
[TARGET / DEFINITION OF DONE]

[ ] Form pendaftaran memproses pendaftaran akun baru dengan data valid secara sukses.
[ ] Sistem menolak registrasi jika email atau nomor WhatsApp sudah terdaftar.
[ ] Konfirmasi password yang tidak cocok memunculkan pesan error yang jelas.
[ ] Bot yang mengisi input honeypot otomatis ditolak oleh sistem.
[ ] Route /signup tidak bisa diakses sama sekali jika registrasi dimatikan di Global Config.
[ ] Setiap user baru otomatis memiliki role 'member' tanpa celah injeksi privilege admin.
[ ] User yang baru mendaftar langsung dialihkan ke dashboard / halaman login dengan status siap pakai.
[ ] Rate limiting IP berhasil menahan flooding pembuatan akun massal.

================================================================================
MODUL: PASSWORD RESET / RECOVERY (CORE MODULE)
================================================================================

[GOAL]
Memfasilitasi pemulihan akses akun mandiri via OTP WhatsApp khusus bagi pengguna 
yang mendaftar secara manual (memiliki password lokal); memproteksi sistem dari spam 
gateway; serta menolak permintaan reset bagi akun yang terdaftar via Google OAuth.

--------------------------------------------------------------------------------
[ACTION]

1. Routing & Antarmuka:
   - Endpoint Permintaan: GET /forgot-password dan POST /forgot-password.
   - Endpoint Verifikasi OTP: GET /verify-otp dan POST /verify-otp.
   - Endpoint Set Password Baru: GET /reset-password dan POST /reset-password.
   - UI Form: 
     a. Form 1: Input nomor WhatsApp terdaftar.
     b. Form 2: Input 6-digit OTP + timer hitung mundur 60 detik.
     c. Form 3: Input Password Baru dan Konfirmasi Password Baru.

2. Provider Check Guard (Pemisah Akun Manual vs Google):
   - Di awal proses POST /forgot-password, periksa status kredensial user:
     a. Jika akun memiliki 'google_id' dan kolom 'password' bernilai NULL, hentikan 
        proses dan tampilkan pesan: "Akun ini terdaftar via Google Sign-In. Silakan 
        langsung masuk menggunakan tombol Masuk dengan Google."
     b. Proses pengiriman OTP HANYA dilanjutkan jika akun memiliki password lokal 
        (password IS NOT NULL).

3. Database Schema:
   - Tabel 'password_resets':
     - id (bigint, PK)
     - user_id (bigint, FK ke users)
     - phone (varchar)
     - otp_hash (varchar, hash dari 6 digit kode OTP)
     - reset_token (varchar, token validasi pembuka form password baru)
     - attempts (int, default 0, batas salah input)
     - expires_at (timestamp, masa berlaku 10 menit)
     - created_at (timestamp)

4. Integrasi WhatsApp Gateway & Anti-Spam:
   - Cooldown Pengiriman: Kunci resend OTP minimal 60 detik per nomor telepon.
   - Rate Limit IP: Maksimal 3 request per jam dari IP yang sama.
   - Format Pesan: "Kode verifikasi reset password kamu: [OTP]. Berlaku 10 menit. 
     JANGAN berikan kode ini ke siapa pun."

5. Verifikasi OTP & Brute Force Guard:
   - Batasi percobaan salah input OTP maksimal 3 kali. Jika melebihi batas, hapus 
     record OTP dan paksa user mengulang dari awal.
   - Jika OTP valid, terbitkan 'reset_token' sementara (aktif 5 menit) untuk 
     membuka form input password baru.

6. Eksekusi Password Baru & Sesi:
   - Validasi panjang password baru minimal 8 karakter.
   - Update tabel 'users' dengan password hash baru.
   - Hapus record token di 'password_resets' agar tidak bisa dipakai ulang.
   - Hapus semua sesi 'Remember Me' user tersebut di tabel 'user_tokens' untuk 
     memutus akses di perangkat lain.

--------------------------------------------------------------------------------
[TARGET / DEFINITION OF DONE]

[ ] Sistem menolak permintaan reset jika akun terdaftar via Google OAuth (password NULL).
[ ] Permintaan OTP hanya berhasil diproses untuk akun manual yang memiliki password lokal.
[ ] Pesan WhatsApp berisi kode OTP 6 digit diterima user terdaftar dalam hitungan detik.
[ ] Tombol kirim ulang terkunci selama 60 detik setelah request pertama.
[ ] Kode OTP kedaluwarsa otomatis dan tidak bisa digunakan setelah 10 menit.
[ ] Upaya salah input OTP lebih dari 3 kali langsung membatalkan sesi pemulihan.
[ ] Form password baru tertolak jika tidak menyertakan reset_token yang valid.
[ ] Password baru langsung aktif untuk login dan token Remember Me lama tercabut.

================================================================================
MODUL: USER & ROLE MANAGEMENT (CORE MODULE)
================================================================================

[GOAL]
Menyediakan panel kendali terpusat untuk mengelola data pengguna (CRUD), status 
akun, serta sistem hak akses dinamis berbasis grup peran (Custom Roles) dengan 
matriks izin granular tingkat halaman (Page-based CRUD: Create, Read, Update, Delete); 
sambil tetap mengunci hak akses mutlak Superadmin (ID 1).

--------------------------------------------------------------------------------
[ACTION]

1. Routing & Otorisasi:
   - Endpoint Pengguna:
     - GET  /admin/users             (Daftar user + filter + pagination)
     - GET  /admin/users/create      (Form tambah user)
     - POST /admin/users             (Simpan user baru)
     - GET  /admin/users/{id}/edit   (Form edit profil & assignment role)
     - POST /admin/users/{id}        (Simpan update user)
     - POST /admin/users/{id}/status (Toggle status: active / banned)
     - POST /admin/users/{id}/delete (Hapus user)
   - Endpoint Custom Roles & Permissions:
     - GET  /admin/roles                  (Daftar grup role)
     - GET  /admin/roles/create           (Form tambah role baru)
     - POST /admin/roles                  (Simpan role baru)
     - GET  /admin/roles/{id}/permissions (Form matriks checklist izin CRUD per halaman)
     - POST /admin/roles/{id}/permissions (Simpan konfigurasi izin role)
     - POST /admin/roles/{id}/delete      (Hapus custom role)

2. Skema Database Role & Permission Matrix:
   - Tabel 'roles':
     - id (bigint, PK)
     - name (varchar, misal: "Content Editor", "Finance Staff")
     - slug (varchar, unique, misal: "editor", "finance")
     - is_system (tinyint, 1 = role bawaan seperti superadmin/member, 0 = custom)
   - Tabel 'role_permissions' (Granular Page CRUD):
     - id (bigint, PK)
     - role_id (bigint, FK ke roles)
     - page_slug (varchar, pengenal halaman/modul, misal: "users", "articles", "settings")
     - can_create (tinyint, 0 atau 1)
     - can_read   (tinyint, 0 atau 1)
     - can_update (tinyint, 0 atau 1)
     - can_delete (tinyint, 0 atau 1)

3. Antarmuka Matriks Permission (Page-based):
   - Di halaman /admin/roles/{id}/permissions, sajikan tabel matriks yang membaca 
     daftar seluruh modul/halaman yang terdaftar di sistem.
   - Baris: Nama Halaman / Modul (Users, Articles, Global Config, dll).
   - Kolom: Checkbox untuk Create [C], Read [R], Update [U], Delete [D], serta 
     checkbox pintasan "Check All" per baris.

4. Permission Guard (Enforcement Engine):
   - Buat helper/gate terpusat di core framework, misal: 
     can('users', 'create') atau Gate::allows('articles', 'delete').
   - Logika Pengecekan:
     a. Superadmin Bypass: Jika role user adalah 'superadmin', return true seketika 
        untuk seluruh aksi tanpa perlu query tabel permission.
     b. Role Khusus: Cek data tabel 'role_permissions' sesuai role_id user, page_slug, 
        dan aksi CRUD yang diminta.
     c. Jika bernilai 0 atau tidak ada relasi, tolak aksi dengan response 403 Forbidden.

5. Proteksi Sistem (System & Superadmin Guard):
   - Role 'superadmin' dan user ID 1 memiliki status mutlak (is_system = 1):
     - Tidak bisa dihapus dari database.
     - Tidak bisa diubah izin dasarnya.
     - Role bawaan sistem tidak bisa di-rename atau dihilangkan.
   - Self-Protection: User tidak bisa menghapus rolenya sendiri atau menghapus 
     akun miliknya sendiri dari panel admin.

6. Manajemen Status Akun & Provider:
   - Panel membedakan visual akun pendaftaran lokal vs akun Google OAuth.
   - Aksi 'banned' langsung mematikan akses, membersihkan token Remember Me di 
     'user_tokens', dan memblokir request berikutnya via Auth Guard.

--------------------------------------------------------------------------------
[TARGET / DEFINITION OF DONE]

[ ] Admin bisa membuat grup role baru (misal: "Staf Penulis", "Operator").
[ ] Admin bisa mengatur izin Create, Read, Update, Delete per modul/halaman 
    lewat form checklist matriks.
[ ] User yang diberi custom role hanya bisa menjalankan aksi CRUD yang diizinkan 
    (misal: bisa buka halaman dan edit, tapi tombol tambah/hapus diblokir).
[ ] Request direct URL untuk aksi terlarang otomatis dicegat oleh Permission Guard 
    (403 Forbidden).
[ ] Role 'superadmin' otomatis memiliki akses 100% tanpa konfigurasi manual.
[ ] Role bawaan sistem (is_system = 1) dan User ID 1 terlindungi dari hapus/edit ilegal.
[ ] Akun dengan status 'banned' langsung terputus dari sesi aktif.

================================================================================
MODUL: GLOBAL CONFIG (CORE MODULE)
================================================================================

[GOAL]
Menyediakan pusat pengaturan operasional sistem terpadu (identitas web, otentikasi, 
integrasi API, dan mode pemeliharaan); mendukung konektivitas multi-database 
(MySQL, PostgreSQL, SQLite) dengan standarisasi prefix pada nama database ('IDIOT_'); 
serta mengelola sistem lokalisasi bahasa dinamis berbasis file auto-discovery 
(default English) dengan pembacaan instan dalam memori.

--------------------------------------------------------------------------------
[ACTION]

1. Routing & Otorisasi:
   - Endpoint:
     - GET  /admin/configs        (Panel pengaturan bertab)
     - POST /admin/configs        (Simpan seluruh konfigurasi)
   - Gate Guard: Hanya dapat diakses oleh user ber-role 'superadmin'.

2. Standarisasi Multi-DB (Database Name Prefix):
   - Database Connection Engine (Core PDO Wrapper):
     - Mendukung 3 driver: 'mysql', 'pgsql', dan 'sqlite'.
     - Aturan Penamaan DB: Prefix 'IDIOT_' diterapkan khusus pada nama database 
       (contoh MySQL/PostgreSQL: database `IDIOT_myapp`; SQLite: `IDIOT_database.sqlite`).
     - Nama tabel di dalam database tetap normal tanpa modifikasi prefix.
   - Skema Tabel 'configs':
     - id (bigint, PK)
     - group (varchar, misal: 'general', 'auth', 'oauth', 'whatsapp', 'localization')
     - key (varchar, unique, misal: 'site_name', 'default_language')
     - value (text, nullable)
     - type (varchar, default 'string')
     - updated_at (timestamp)

3. Dynamic Language Auto-Discovery Engine:
   - Struktur Folder: `languages/` (atau `app/Languages/`).
   - Format File: `language.{code}.php` (contoh: `language.en.php`, `language.id.php`).
     Tiap file mengembalikan array translasi: `return ['welcome' => 'Welcome', ...];`.
   - Auto-Discovery Scanner:
     - Engine memindai folder menggunakan pola `glob('languages/language.*.php')`.
     - Ekstrak kode bahasa dari nama file secara dinamis via regex/string parser.
     - Setiap ada penambahan file baru (misal: `language.tk.php`), bahasa 'tk' 
       otomatis terdaftar ke sistem dan langsung muncul sebagai opsi di UI admin 
       maupun language switcher publik tanpa perlu restart aplikasi atau ubah database.
   - Default & Fallback:
     - Nilai bawaan sistem: English ('en').
     - Sediakan helper translasi global: `__('key')` atau `lang('key')`.
     - Jika kata kunci tidak ditemukan pada bahasa aktif, otomatis fallback ke 
       frasa dari `language.en.php`.

4. Kategori Pengaturan di Antarmuka UI (Tabbed Layout):
   - Tab General:
     - Nama Situs, Deskripsi, Base URL, Favicon & Logo.
     - Default Language: Dropdown pilihan bahasa yang isinya terisi otomatis 
       dari hasil scan file `language.*.php` yang tersedia di folder bahasa.
   - Tab Auth & Registration:
     - Toggle registrasi publik (allow_registration).
     - Batas percobaan brute force login.
   - Tab Google OAuth:

- Terapkan skala tipografi yang jelas dan sistem spacing 8pt agar hierarki visual tegas tanpa perlu banyak garis tepi (border).

2. Fluent Micro-Feedback
- Berikan respons instan pada setiap aksi pengguna (efek hover, focus, atau pembukaan modal).
- Gunakan transisi CSS yang sangat singkat (150ms - 200ms) agar antarmuka terasa hidup dan tidak kaku.

3. Token Desain Terpusat
- Kelola warna, jarak, dan border-radius menggunakan variabel CSS atau utility classes.
- Struktur terpusat ini memudahkan iterasi desain tanpa perlu mengubah banyak kode UI.

4. Responsive, minimal untuk tablet dan desktop.

KOMPATIBILITAS DENGAN HTMX

HTMX memperbarui halaman lewat pertukaran (swap) HTML parsial dari server. UI/UX dirancang agar transisi pergantian konten ini berjalan mulus dan terasa sehalus Single Page Application (SPA).

1. State Loading & Indicator
- Manfaatkan kelas bawaan .htmx-request untuk otomatis menampilkan spinner atau skeleton screen saat proses HTTP berjalan.
- Gunakan wadah (container) bernilai tinggi atau lebar tetap untuk mencegah pergeseran tata letak (layout shift).

2. Transisi Swap Mulus (CSS Transitions)
- Terapkan kelas .htmx-swapping dan .htmx-settling untuk memberikan efek fade-in halus saat elemen baru masuk.
- Hindari pergantian konten secara mendadak agar mata pengguna tidak kaget.

3. Komposisi Komponen Parsial
- Pecah UI menjadi komponen kecil (card, baris tabel, form) yang bisa di-render ulang secara independen menggunakan hx-target dan hx-swap="outerHTML".

4. Interaksi Out-Of-Band (OOB)
- Pakai hx-swap-oob="true" untuk memperbarui elemen pendukung di luar target utama (misalnya memperbarui badge counter atau memunculkan toast notification secara bersamaan).
